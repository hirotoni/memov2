# PLAN

## Goal

Close out the backlog item "検索機能: タイトル直下のコンテンツは検索に引っかからない"
by (a) adding regression test coverage proving that `search.SearchMemo` already
correctly indexes body text placed directly under a memo's `# Title` heading
(before the first `##` heading), and (b) removing the now-inaccurate
"Limitations" note in `README.md` and the corresponding `backlog.md` entry,
since the behavior they describe does not reproduce in the current code.

## Current Findings

- `internal/search/search.go:64-89` already folds `memo.TopLevelBodyContent().ContentText`
  into every `MatchContent`/`MatchHeading` search, in addition to `HeadingBlocks()`
  (search.go:92-131), `Title()` (search.go:42), and `CategoryTree()` (search.go:50-60).
- `TopLevelBodyContent()` (`internal/domain/file.go:33-38`) is populated at load
  time by `internal/utils/handler.go:161-198`, invoked from
  `internal/repositories/memo/memo.go:142` on every file read. This parser-level
  behavior is already unit-tested (`internal/utils/handler_test.go:220-246`,
  "document with top level content").
- Verified empirically this session: saved a memo via `repo.Save` with
  `SetTopLevelBodyContent` set, reloaded it via `repo.Memo` (the real production
  load path), and ran `search.SearchMemo(..., MatchContent)` against it — the
  top-level text was found. The bug as described in `README.md:181` and
  `backlog.md:5` does **not** reproduce for a well-formed memo file.
- `internal/search/search_test.go` never calls `SetTopLevelBodyContent` on its
  test fixture, so there is currently **no regression test** proving this path
  works end-to-end through `SearchMemo`. That is the real, actionable gap.
- A related but distinct and already-intentional behavior: if a memo file's
  body doesn't start with a level-1 heading, `memo.go:142-145` returns an error
  and `scanDirectory` (`memo.go:77-85`) skips that file entirely (with a
  warning), removing it from browse/search/weekly/index alike. This is **not**
  a bug — it is deliberately covered by
  `TestMemoEntries_SkipsUnparseableFiles` (`internal/repositories/memo/memo_test.go:236-268`)
  and matches the repo's established "a single bad file must not break
  listing/search" pattern (see comment at `memo.go:81-82`). Out of scope; must
  not be changed by this pass.
- `docs/plans/plan_20260704081955.md` (committed earlier today) already
  recorded this exact backlog item as "reproduction uncertain" when triaging
  what to work on next — this pass resolves that uncertainty with a concrete
  answer (not reproducible for well-formed files) and closes it out.

## Decisions

- Do not modify `internal/search/search.go`, `internal/utils/handler.go`, or
  `internal/repositories/memo/memo.go`. The searchable behavior is already
  correct; the only gap is missing test coverage and stale docs.
- Add regression coverage in `internal/search/search_test.go` rather than a new
  test file, to keep it alongside the existing `TestSearchMemo` table test.
- Remove the `## Limitations` section from `README.md` outright (its one
  bullet is the only content in that section) rather than rewording it, since
  after this pass there is no remaining limitation to document.
- Remove only the leaf bullet under `backlog.md`'s `検索機能` item (the
  "タイトル直下のコンテンツ..." line), leaving the `検索機能` / `memo 機能`
  parent labels in place as they may hold future items.
